01 — Paradigmas

Evolução & Paradigmas
de Desenvolvimento

A engenharia de software evoluiu ao longo de décadas, passando por crises, revoluções e consolidações de boas práticas que formam os alicerces do desenvolvimento moderno.

1950–1960

Era da Programação Artesanal

Software escrito em linguagem de máquina ou Assembly por especialistas altamente técnicos. Não havia metodologia formal — a criação era puramente intuitiva e dependia do talento individual.

1968

Crise do Software

A Conferência de Garmisch cunhou o termo "Crise do Software": projetos sistematicamente atrasados, acima do orçamento e com falhas críticas. Nasce a necessidade de uma engenharia formal.

1970–1990

Paradigma Estruturado

Surgem linguagens de alto nível, programação estruturada (sequência, seleção, repetição), modularização e as primeiras metodologias formais como o Modelo Cascata de Royce (1970).

1990–2000

Paradigma Orientado a Objetos

Encapsulamento, herança e polimorfismo revolucionam o design. Surge a UML (1997) como linguagem de modelagem unificada. Java, C++ e Smalltalk dominam o cenário empresarial.

2001–presente

Era Ágil, Cloud e IA

O Manifesto Ágil (2001) redefine prioridades. A computação em nuvem, microsserviços, DevOps e agora a IA generativa reconfiguram completamente como o software é pensado, desenvolvido e entregue.

∫

Estruturado

Fluxo de controle explícito. Funções e procedimentos como unidades básicas. Base da programação imperativa clássica.

  • C
  • Pascal
  • COBOL
⬡

Orientado a Objetos

Modelagem baseada em entidades do mundo real. Encapsulamento, herança e polimorfismo como pilares fundamentais.

  • Java
  • C#
  • Python
λ

Funcional

Funções puras, imutabilidade e ausência de efeitos colaterais. Ideal para sistemas concorrentes e de alta confiabilidade.

  • Haskell
  • Erlang
  • Clojure
⚡

Reativo / Orientado a Eventos

Sistemas que respondem a fluxos de dados assíncronos. Base do desenvolvimento moderno de front-end e microsserviços.

  • Rx
  • Node.js
  • Kafka
02 — Ética

Aspectos Éticos no
Desenvolvimento de Software

O poder de criar software traz responsabilidades profundas: privacidade, impacto social, viés algorítmico e sustentabilidade são questões centrais da engenharia moderna.

01

Privacidade por Design

A proteção de dados não é um add-on — é um requisito de arquitetura. Princípios GDPR/LGPD, minimização de dados e consentimento explícito devem ser embutidos desde o início do projeto, não adicionados ao final.

02

Responsabilidade Algorítmica

Algoritmos podem perpetuar ou amplificar preconceitos existentes. Engenheiros têm a responsabilidade ética de auditar modelos de ML, verificar distribuições de treinamento e documentar limitações de sistemas automatizados.

03

Acessibilidade Universal

Software que exclui pessoas com deficiências é antiético e, em muitos países, ilegal. As diretrizes WCAG 2.1 devem ser requisitos de aceite, não melhorias futuras — acessibilidade é direito, não feature.

04

Transparência & Explicabilidade

Sistemas que tomam decisões impactantes (crédito, saúde, justiça) devem ser explicáveis. O "caixa-preta" é eticamente inaceitável quando afeta direitos fundamentais de pessoas.

05

Segurança como Obrigação

Negligenciar segurança não é apenas um risco técnico — é uma falha ética. Práticas como SAST, testes de penetração, gestão de vulnerabilidades e disclosure responsável são deveres profissionais.

06

Impacto Ambiental

Green software engineering mensura e reduz a pegada de carbono do desenvolvimento. Escolhas arquiteturais (serverless, otimização de queries, compressão de dados) têm impacto ambiental real e mensurável.

"Com grande poder computacional vem grande responsabilidade. O código que você escreve hoje pode afetar milhões de vidas amanhã."
— ACM Code of Ethics & Professional Conduct
03 — Arquitetura

Fundamentos de
Arquitetura de Software

Arquitetura de software é a estrutura fundamental de um sistema: seus componentes, suas relações e os princípios que guiam seu design e evolução ao longo do tempo.

Objetivos Fundamentais

⚙ Escalabilidade

Capacidade de crescer horizontalmente ou verticalmente sem reescrever o sistema central.

🛡 Confiabilidade

Operação correta mesmo sob falhas parciais, com resiliência e recuperação automática.

🔧 Manutenibilidade

Facilidade de entender, modificar e evoluir o sistema sem introduzir regressões.

⚡ Performance

Tempo de resposta e throughput adequados às necessidades reais dos usuários.

🔒 Segurança

Proteção contra ameaças, com autenticação, autorização e criptografia adequadas.

🔗 Interoperabilidade

Capacidade de integrar-se com outros sistemas via padrões abertos e APIs bem definidas.

Orientada a Eventos

Comunicação assíncrona via mensagens. Desacoplamento máximo entre produtores e consumidores. Base do streaming de dados.

Princípios SOLID

S
Single Responsibility

Uma classe deve ter apenas um motivo para mudar.

O
Open/Closed

Aberto para extensão, fechado para modificação.

L
Liskov Substitution

Subtipos devem ser substituíveis por seus tipos-base.

I
Interface Segregation

Interfaces específicas são melhores que uma interface geral.

D
Dependency Inversion

Dependa de abstrações, não de implementações concretas.

04 — Ciclo de Vida

Ciclo de Vida
do Software (SDLC)

O SDLC (Software Development Life Cycle) é um processo estruturado que define as fases pelas quais um sistema passa, do conceito à aposentadoria.

1

Levantamento de Requisitos

Identificação das necessidades dos stakeholders. Técnicas: entrevistas, workshops, prototipagem, análise de documentos e observação. Resultado: especificação funcional e não-funcional.

Documento de Requisitos User Stories Casos de Uso
2

Análise & Design

Modelagem da solução: arquitetura, banco de dados, fluxos de dados, interfaces e integrações. Uso de UML, ERD, wireframes e protótipos de alta fidelidade.

Diagramas UML Protótipos Arquitetura
3

Implementação

Codificação seguindo padrões definidos. Code review, pair programming, TDD (Test-Driven Development) e continuous integration garantem qualidade durante o desenvolvimento.

Código-fonte Testes Unitários Documentação Técnica
4

Testes & Qualidade

Verificação e validação em múltiplos níveis: unitário, integração, sistema, aceitação (UAT), performance e segurança. Gestão de defeitos com rastreabilidade.

Plano de Testes Relatórios de QA Métricas de Cobertura
5

Implantação

Deploy em produção com estratégias de rollout seguro: blue-green, canary release, feature flags. Monitoramento pós-deploy com observabilidade (logs, métricas, traces).

Pipeline CI/CD Runbook Plano de Rollback
6

Manutenção & Evolução

Correção de bugs, melhorias de performance, adaptações a mudanças de requisitos e tecnologias. Refactoring contínuo para gestão de dívida técnica.

Gestão de Mudanças SLA / SLO Backlog de Melhorias

Modelo Cascata

Royce, 1970

O modelo mais clássico: fases sequenciais e lineares onde cada fase deve ser completada antes da próxima começar. Simples de entender e gerenciar, mas inflexível a mudanças.

Modelo Incremental

Mills, 1980

Divide o sistema em incrementos funcionais entregues progressivamente. Cada incremento adiciona funcionalidade ao anterior, permitindo feedback mais cedo e entrega parcial de valor.

Frameworks Ágeis

Scrum

Framework iterativo com sprints de 1-4 semanas. Papéis definidos: Product Owner, Scrum Master e Dev Team. Cerimônias: Planning, Daily, Review e Retrospective.

SprintsProduct BacklogVelocity

Kanban

Visualização do fluxo de trabalho em colunas (To Do → In Progress → Done). Foco em limitar WIP (Work in Progress) e otimizar o fluxo contínuo sem iterações fixas.

XP (Extreme Programming)

Práticas técnicas rigorosas: TDD, pair programming, refactoring contínuo, integração contínua e releases pequenos e frequentes. Qualidade de código acima de tudo.

CI — Integração Contínua

Cada commit dispara build automatizado e suite de testes. Falhas são detectadas imediatamente. O branch principal está sempre em estado deployável.

CD — Entrega Contínua

Software sempre pronto para deploy em produção após passar pelo pipeline. A decisão de release é humana, mas a capacidade técnica é automatizada e confiável.

CD — Deploy Contínuo

Toda mudança que passa pelo pipeline é automaticamente colocada em produção. Requer confiança extrema nos testes automatizados e infraestrutura de rollback.

Observabilidade

Logs estruturados, métricas de negócio e técnicas, e distributed tracing formam o tripé da observabilidade — essencial para operar sistemas distribuídos modernos.
